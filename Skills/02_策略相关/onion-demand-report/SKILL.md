# 外部需求报告

## 目的

回答：用户指定的目标时间节点下，当前采集批次中有哪些可回源的具体需求证据。

报告不判断产品能否承接，不读内部报告，不测市场占比，不生成购买动因。正式产物是一份可被人和下游完整读取的 Markdown，不拆详情目录，不生成机器台账。

## 运行前读取

- 使用当前已部署数据工具时读取[HTTP MCP适配](../../references/http-mcp-adapter.md)；
- 冻结数据和控制模型上下文时读取[四份报告上下文与 Token 合同](../../references/report-context-efficiency.md)；
- 写两份需求报告的共同字段时读取[需求卡共同接口](../references/demand-card-contract.md)；
- 确定批次和证据事实时读取[取数事实合同](references/data-requirements.md)；
- 拆分、筛选和归并需求时读取[需求规则](references/demand-rules.md)；
- 写报告时使用[报告模板](references/report-template.md)。

## 用户输入

用户必须指定本次报告服务的目标时间节点，例如“开学前”、“开学适应期”或“期中前”。目标时间节点决定筛选什么需求，不是外部证据的采集日期。

用户没有提供目标时间节点时，只询问这一项，不自动推算，不生成正式报告。

正式业务取数使用统一 HTTP `onion-agent` OAuth MCP；只有用户明确提供冻结导出文件时才使用导出输入。不得由本 Skill 直连数据库、SSH或对象存储。

## 固定流程

1. 解析用户的目标时间节点；无法解析成真实学习阶段时停止并询问。
2. 冻结当前外部采集批次，记录批次身份、实际采集范围、来源和冻结时刻。调用一次`intelligence_freeze_report_input(mode=external-demand)`由服务器完成后续全部分页和守恒；下载返回的快照ZIP、校验SHA-256，再用`Skills/scripts/extract_report_input_snapshot.py`展开到`.runtime`。外层对话只接收 manifest，不读取每页正文。
3. 从冻结快照完整取得批次内内容、评论和广告需求证据，核对稳定证据数、独立语境数、来源构成和缺口。模型只读取去掉 transport envelope 的完整业务记录，不能重复调用同一列表或把原始页再次插入上下文。
4. 将每条证据拆成一个或多个单核心问题的需求单元，保留来源身份和回源。
5. 只保留与目标时间节点具有真实任务、问题或期待变化关系的需求单元；不为凑节点改写证据。
6. 按需求主体、学习/家庭任务、核心问题机制和期待变化语义归并；关键词或检索只发现候选。模型输入超过一个有界批次时，批内任务只输出稳定证据ID和需求语义，跨批任务只读取候选定义与中心/边界证据；全部稳定证据ID必须有且仅有一个正式归属或排除去向。
7. 为每个最终需求簇继续拆解“同一核心问题的具体表现”和“大家现在怎么处理”，各归纳1至4类并使用简洁列表展示。不同核心问题仍必须拆成不同需求，不能用详情列表重新合并。
8. 写出“这个时间节点下发生了什么”，只记录当前数据中能看到的任务、紧迫性或处理顺序变化，不写合理推演。
9. 数据层继续计算证据对象数、独立来源语境数和来源构成，用于守恒、排序和问题回溯；这些计数不进入业务报告。每条需求选择1至3条可点击的原始内容，用来证明需求有真实来源。
10. 在不继承当前长对话的隔离模型上下文中，通过一个有界任务或map/reduce生成语义映射或报告正文；后续计数、排序、链接和 Markdown 校验使用确定性脚本。生成单文件报告：一览只保留需求名称、主体、人群和跳转；具体场景、问题、当前应对、期待变化、具体表现拆解和原始内容只进入详情。最后运行 `scripts/validate_report.py <报告>`。

## 完整性与边界

- 只使用当前采集批次，不补历史同节点证据；
- 范围、分页或稳定证据总数无法守恒时停止；
- 某一来源缺失但其他来源完整时可继续，报告标记部分完整；
- 1条合格外部内容或评论也可以形成需求，但默认不进入本期主要结论；
- 广告可以形成需求证据，但必须写广告表达，不冒充用户原话；
- 证据数量不代表市场人数、占比或购买概率。

## 修改已有报告

只改表达时继承原目标时间节点和证据成员；改归并或时间节点适配时重算受影响需求；更新数据时重新冻结当前批次。所有修改生成新版本，不覆盖旧文件。

## 完成标准

- 报告头明确记录用户目标时间节点和外部数据批次；
- 每条需求都对应目标时间节点，并使用共同需求定义表；
- 每条需求的数据层成员、来源构成和代表链接守恒；
- 需求一览的“查看详情”与显式详情锚点一一对应；
- 一览不重复完整需求定义；详情额外展示具体表现拆解、时间节点任务变化和当前做法；
- 报告是单个、紧凑、可完整读取的 Markdown；
- 校验器通过后才交给购买动因或功能方向卡。
